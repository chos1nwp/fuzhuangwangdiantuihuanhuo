## 三、并发与可见性专项

### 场景 7：两个客服同时同意退回

| 步骤 | 操作 | 预期结果 |
| --- | --- | --- |
| 1 | 消费者新建一张「待客服审核」的售后单 | 状态 `pending_review`，可被处理 |
| 2 | 苏晴（`13900000001`）与何楠（`13900000002`）同时提交「同意退回」 | 一个 200 成功，另一个 409「该售后单刚被其他人处理，请刷新后重试」 |
| 3 | 查询该单时间线 | 只有 1 条 `approve` 记录，状态只前进一次 |
| 4 | 用旧状态再次提交 | 409，不会出现覆盖或重复生成退回地址 |

实现方式：`UPDATE cases SET ... WHERE id=? AND status=?`，影响行数为 0 时在事务内抛错回滚。

## 五、结论

- 9 条核心验收场景全部通过（自动化 47 项断言）。
- 关键业务规则均有服务端校验，不能通过修改前端绕过。
- 并发处理同一张售后单由状态条件更新兜底，重复处理后到一方收到 409，不会产生重复退款或重复补发。
- 内部作业记录在服务端过滤，消费者无法通过接口拿到仓库备注与验货明细。
- 未发现阻塞使用的缺陷；已知限制（内存会话、模拟资金）属于首版设计范围。
